# Security for the free parent pilot

This repository is preparing a free pilot shared with nearby parents. The URL is public, with no login or invite-only authentication; invitations provide a private feedback contact, not an access restriction. Device cookies identify push records rather than authenticated parent accounts. Real iOS/Android consent, unsubscribe, delivery, freshness and parent usability acceptance are not yet verified. Commercial operator identity/public contact details, legal/rights review, independent security assessment, encrypted subscription recovery and tested failover remain pending. A published security email and guaranteed response SLA are not available. Free use is not a claim of exemption from data-protection obligations.

## Private reporting

Contact the person who invited you to the pilot using your existing private channel. Ask them to forward the report to the responsible maintainer. Do not publish a vulnerability, child's identity, parent details, raw push endpoint, `auth`/`p256dh` values, access token or database dump in an issue or chat. Provide the approximate time, device/browser, app revision if known, expected/actual behavior and a redacted screenshot or safe reproduction. Use synthetic data for testing and stop if you encounter another person's data. The maintainer should acknowledge reports through the inviter and agree on follow-up privately; no unverified address or response guarantee is advertised.

## Data and recovery boundaries

Do not collect children's names, childcare attendance, class rosters, private school messages, photos or exact household location. Only public-source notices and minimal school/grade/source filters belong in the catalog. Push endpoints and subscription encryption/authentication values are sensitive and must live in a separate restricted store; secrets belong in hosting secret storage. Exclude subscription storage from unencrypted hosting snapshots, exports and debug logs.

`python -m sakurano_line_notifier.ops` backs up only the recognized public `catalog_results` SQLite schema. It refuses push/subscription schemas and filenames and unknown/mixed databases. Snapshots use SQLite online backup, integrity checks, private files and atomic bundle publication. Restore validates a manifest and actual copied bytes and requires a new destination; it never replaces an existing DB. Retention is limited to intact managed bundles in the supplied directory. A checksum is not authentication, and file mode `0600` is not encryption. Trust the backup directory and serialize maintenance; schema validation cannot determine whether an operator put private content into a public payload.

Push subscriptions, consent, notification history, provider credentials and full service recovery are outside this backup. After subscription loss or key compromise, pause push, notify through inviters and obtain fresh explicit device consent for a new subscription. Never rebuild secrets from logs or silently re-enroll users. See [pilot operations](docs/PILOT_OPERATIONS.md) for commands, acceptance gates and the incident runbook.

## Containment and release checks

To stop collection and sending, set `WEB_PUSH_ENABLED=false`, restart the instance and verify disabled configuration, refused same-origin enrollment and no storage growth. If that control is unavailable or uncertain on the deployed revision, block `POST /api/push/subscribe` at the hosting edge or stop the service. Removing only the private VAPID key can leave enrollment enabled; removing the SQLite path may activate a different configured store. Stop old processes and scanners, revoke exposed provider credentials, rotate keys where appropriate, restrict access and share only redacted incident evidence. Current code provides device-owned unsubscribe/privacy-delete routes and browser controls; keep notification collection gated on demonstrated server-side withdrawal and real-device checks, including lost-cookie cases. These controls require runtime verification; this documentation does not change hosting configuration.

CI runs offline unit tests and JavaScript syntax checks and audits configured `requirements.txt` using the [official pip-audit action](https://github.com/pypa/gh-action-pip-audit), including a weekly scheduled run once on the default branch. Review dependency/action updates weekly and before pilot expansion; resolve findings in separate reviewed changes and verify the actual release environment too. Direct requirements are pinned, but transitive pins/hashes are pending, and pip-audit does not certify application security. Do not hide findings or automatically apply fixes to a running pilot.

Use the [PPC general guidelines](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/) and [PPC incident guidance](https://www.ppc.go.jp/personalinfo/legal/leakAction/) as primary inputs to qualified review of data handling and any incident obligations. This policy is an operational commitment for the proposed pilot, not a legal opinion or commercial-readiness certification.
