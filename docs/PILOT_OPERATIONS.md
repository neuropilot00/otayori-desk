# FREE parent pilot operations

Scope: a free trial shared with nearby parents, followed by a separately reviewed commercial phase. The public URL has **no login or invite-only authentication**; an invitation is a sharing/contact arrangement, not an access control. Anyone with the URL may read public notices. Device-cookie ownership for push records is not a parent account or proof of eligibility. No billing, advertising, commercial readiness claim, or school endorsement is implied. Public operator profile/business data is deferred; an inviter must still privately connect each tester to a responsible maintainer before testing. This document is an operational plan, not evidence of deployed controls or legal compliance.

## Acceptance before invitations

All real-parent/device items below are **not yet verified**. Record date, tester alias, device/OS/browser, app revision, result and redacted evidence. Never put a child's name, class roster, childcare attendance, private school message, photograph, exact home location or push endpoint into test records. School/grade/source filters are sufficient; do not solicit parent or child identities in the app. Review public source content for identifiable children too; publicly accessible does not mean unrestricted reuse.

- [ ] A small local parent group understands that this is free and experimental, knows the inviter contact, can read notices without agreeing to push, and uses original school communications for urgent decisions.
- [ ] On real iOS and Android devices, record the installed/home-screen/browser context and test an explicit user gesture to opt in; test denial, dismissal and permission revoked in device settings. No automatic permission prompt or coerced consent.
- [ ] Explain endpoint/key storage, school/grade scope, notification purpose and withdrawal before collecting push data. Verify only the chosen scope receives a controlled new notice, without broadcasting to other parents or flooding historic notices.
- [ ] Verify withdrawal both in the browser/device **and in server storage**, including after restart. Current code has `POST /api/push/unsubscribe` and `POST /api/privacy/delete`, device-cookie ownership and corresponding browser controls. Unit tests do not prove real-device withdrawal. Test each route, deleted delivery state, browser subscription removal, revoked permissions and lost-cookie recovery; browser permission changes alone do not prove server erasure. Use a read-only pilot with collection disabled until these checks pass. An inviter-assisted procedure is needed for records no longer identified by a device cookie.
- [ ] Verify failed opt-in/network/provider requests show understandable errors and allow retry without false success. Confirm stale upstream content has understandable warnings, usable last-known notices and original-source links. `/api/health` is liveness; `/api/ready` checks catalog DB read readiness and is the current Railway health-check target. Neither proves source freshness or push delivery; verify those separately.
- [ ] Compare a real source's publication date, relevant issue/month, grade, original link and app scan timestamp. A September publication with October activities must retain its actual publication date. Confirm manual refresh and background refresh, source failure, and restart using cached public results.
- [ ] Parents can change school/grade, find after-school information and events, follow an original notice, and report a confusing or incorrect item via the inviter. Confirm these on real small screens with parents, not just developer tests.
- [ ] Complete a catalog backup/restore drill on temporary paths, single-instance restart/volume check, secrets/log review, and incident collection-block drill. Keep the evidence private and redacted.

## Runtime boundaries

Run **one web instance** with one attached persistent SQLite volume, HTTPS at the hosting edge, restricted volume access and adequate disk space. Set `WEB_PUBLIC_ORIGIN` to the exact HTTPS origin used by parents; verify same-origin mutation checks and Secure/HttpOnly/SameSite device cookies through that edge. Set `WEB_CATALOG_CACHE_PATH` to a dedicated public-only file such as `/data/catalog_cache.sqlite3`; if notifications pass the gates, use a separate `WEB_PUSH_DATABASE_PATH` such as `/data/push_subscriptions.sqlite3`. Confirm the deployed Railway health check uses `/api/ready`, and verify unreadable/corrupt catalog storage makes readiness fail without exposing paths or credentials; keep `/api/health` as a separate liveness signal. Keep backup storage outside the live database directory and web-served files. Never combine public catalog and subscriptions into one DB. Do not enable additional replicas against local SQLite or claim automatic failover. A PostgreSQL push adapter and scanner exclusion controls exist, but multi-instance catalog coordination and failover still require design and verification.

Put VAPID private keys, PostgreSQL credentials (if introduced), LINE tokens and recipient identifiers in the hosting secret manager, with least-privilege maintainer access. Do not commit `.env`, tokens, raw subscription JSON, volume exports or database files. `WEB_PUSH_PUBLIC_KEY` is public configuration; `WEB_PUSH_PRIVATE_KEY` is a secret. `WEB_PUSH_CONTACT` must use a real, controlled contact when sending is enabled, not a sample address. Keep `NOTIFY_EXISTING_ON_FIRST_RUN=false` for the separate LINE automation unless a reviewed backfill is intended.

For a read-only pilot, set `WEB_PUSH_ENABLED=false`, restart the instance, and verify `/api/push/config` reports both enrollment and sending disabled. Current `WebPushNotifier.subscribe()` rejects enrollment when `browser_enabled` is false; that property honors this switch. Verify a synthetic same-origin subscription with current consent is refused and storage does not grow; keep unsubscribe/privacy-delete available for existing testers. Removing only the private key stops sending but can leave enrollment enabled. If the running revision lacks the switch or verification fails, block `POST /api/push/subscribe` at the HTTPS edge or stop the instance. Do not remove only the database path: configuration can fall back to JSON or PostgreSQL via `DATABASE_URL`. These are deployment instructions to verify, not runtime configuration changes made by this patch.

## Public catalog backup CLI

Run from the repository root using the existing virtual environment (or `python` with Python 3.11+). The CLI itself uses only the standard library and makes no network requests. Use an explicit, dedicated, operator-controlled backup directory on a POSIX filesystem supporting atomic rename, hard links and fsync. Ancestor directories must be trusted and private; no other process may mutate bundles or run backup/restore/retention concurrently. Final input files and backup-directory symlinks are refused. New bundle directories are `0700`; database and manifest files are `0600`. Existing backup-parent permissions are not silently changed; check them yourself.

```sh
python -m sakurano_line_notifier.ops backup \
  --database /data/catalog_cache.sqlite3 \
  --destination /private-backups/public-catalog \
  --keep 7
```

`--destination` for backup is a **directory**, not a filename. The command prints JSON with the published bundle path, for example `/private-backups/public-catalog/catalog-backup-<UTC timestamp>-<UUID>`. It opens the existing source read-only and uses SQLite's online backup API within a read transaction, including committed WAL data without a raw live-file copy. Uncommitted changes are excluded. The copy must match the current six-column `catalog_results` schema; other tables, views, triggers, extra columns and push/subscription object names are refused. Push/subscription filenames are also refused. Never repurpose a DB that held secrets as a catalog DB; this schema check is not a content privacy classifier. Only reviewed public catalog payloads belong here.

The private temporary snapshot is switched to a standalone rollback journal, integrity-checked and vacuumed to discard free pages. The manifest records format/schema, UTC creation time, bundle name, file size, SHA-256 and `integrity_check=ok`, without the source path or data. Both files are fsynced and the complete directory is atomically renamed into place. Readers never see a database without its manifest. Source contention times out after about 30 seconds; disk/permission/integrity failure returns nonzero, with no published partial snapshot or pre-publication pruning. A crash can leave a private `.catalog-backup-*` temporary directory; review it manually. If publication succeeded but retention failed, the command returns nonzero and the complete new bundle may remain; inspect the directory before retrying.

Retention defaults to seven valid bundles and accepts `--keep 1` through `--keep 100`. It considers only direct child directories with the exact managed name, a matching manifest, exactly the two expected regular files, matching checksum/size and passing schema/integrity checks. It removes only those two files and their empty directory. No recursive retention deletion, outside-directory search, deletion of the live source, arbitrary `*.sqlite3` pruning, or symlink traversal is used. Unknown, damaged, incomplete or operator-modified bundles are skipped and need manual review; their count/space is not bounded by `--keep`. Serialize commands and monitor disk usage. Backups are manual: this addition does not schedule jobs. Before a trial, perform a daily backup and a pre-change backup; the latest successfully checked snapshot determines actual catalog recovery loss.

## Restore drill and recovery limits

Choose the exact complete bundle printed by backup and an unused database filename whose parent already exists:

```sh
python -m sakurano_line_notifier.ops restore \
  --backup /private-backups/public-catalog/catalog-backup-<UTC timestamp>-<UUID> \
  --destination /data/catalog_recovered.sqlite3
```

Replace the example bundle placeholder with a real path. Restore requires its manifest, copies into a private temporary file beside the destination, verifies checksum/size, public-only schema and SQLite integrity on the actual copy, then uses an atomic hard-link publication that cannot replace a raced-in file. An existing database, directory, symlink (even dangling), or `-wal`, `-shm` or `-journal` sidecar causes refusal. There is deliberately no overwrite/force flag. Hashes detect corruption; they are not signatures, encryption, or protection against a malicious maintainer changing both files. Accept bundles only from trusted storage.

For a drill, restore to a temporary location, inspect `PRAGMA integrity_check`, compare sample cached source/date/payload fields, and record the manifest timestamp and elapsed recovery time. For actual recovery, stop the instance, restore to a **new** path, point `WEB_CATALOG_CACHE_PATH` at that path, restart the single instance and verify a real notice and freshness. Leave the original DB untouched for investigation; do not copy over a running DB. Keep subscriptions isolated during this drill.

This is **catalog-cache recovery, not full disaster recovery**. It does not back up push subscriptions or scope state, JSON fallback subscriptions, PostgreSQL, LINE state, secrets, source registry/configuration or deployment assets. The catalog itself may be rebuilt from reviewed public sources. Unencrypted backups must never retain push endpoints, `p256dh`/`auth` values or VAPID private keys. Inspect hosting automatic volume snapshots too: they may include the subscription store despite this CLI's refusal; exclude that store from unencrypted snapshots or keep collection disabled. `0600` does not encrypt a backup.

If push storage is lost or keys are revoked, pause collection/sending, communicate via inviters, rebuild an empty separate store, and ask each parent to explicitly re-consent and re-subscribe on their device. With a new VAPID key pair, stale browser subscriptions may need removal first; verify that with real devices. Do not reconstruct secrets from logs, import unknown dumps, silently re-enroll users or claim restoration of prior consent/deduplication state. Confirm a clean baseline avoids historical notification floods before sending. Secure, encrypted subscription recovery with key custody and restore drills is future work.

## Incident runbook

1. Receive reports privately through the inviter, who forwards them to the maintainer. Record UTC time, affected revision, category and redacted reproduction. Do not ask for subscription endpoints, auth keys, children's names or raw database dumps. If urgent, stop the service immediately.
2. Set `WEB_PUSH_ENABLED=false` and restart/stop the old process; verify disabled enrollment/sending and that a synthetic subscription is refused without storage growth. If the running version or edge verification is uncertain, block `POST /api/push/subscribe` at the edge or stop the instance. Remove compromised `WEB_PUSH_PRIVATE_KEY` and related keys from hosting secrets so old processes cannot retain them in memory. Stop any separate LINE/push scanner. A hidden button or disabled sending alone is insufficient containment; preserve withdrawal access where safe.
3. If exposure is suspected, revoke provider tokens/credentials and rotate VAPID keys through controlled secret storage. VAPID key rotation does not delete browser subscriptions or guarantee remote revocation of all old registrations; plan re-consent. Restrict compromised storage/admin access. Preserve necessary evidence only in restricted encrypted incident storage; keep public catalog recovery separate.
4. Redact authorization headers, cookies, database URLs, endpoint query strings, `auth`, `p256dh`, VAPID keys, LINE tokens/recipient IDs, child/parent identities and full request bodies before sharing logs. The app currently suppresses request logging, but edge/provider/hosting logs must be reviewed separately. Share error class, route category, timestamp and counts only; never enable body/secret logging for diagnosis.
5. Assess affected records and dates, correct the cause, privately notify affected testers through their inviters, and obtain advice on any applicable reporting/notification obligations. Use the PPC references below for that review; do not infer that a free beta has no obligations. Reopen only after containment, withdrawal and recovery have been verified and the maintainer records the decision. No guaranteed response SLA or failover is claimed.

## Dependency maintenance and commercial gates

The CI workflow runs repository `unittest` tests, syntax-checks `web/app.js`, `web/sw.js` and `web/policies.js` using runner Node, and uses the official pip-audit action with **`inputs: requirements.txt`**, including dependency resolution. It runs on pushes, pull requests, manual dispatch and Mondays at 03:17 UTC; scheduled runs require the workflow on the default branch and enabled GitHub Actions. Maintainers must check GitHub failure notifications/settings; the schedule does not guarantee a separate alert service. Unit tests are offline and use temporary/synthetic data; dependency install and audit require network access and must fail visibly on outages or findings. No automatic `--fix`, ignored findings, or upload of runtime databases/secrets is configured. Use GitHub-hosted current runners. CI has not been executed remotely by this change.
